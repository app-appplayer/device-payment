## 0. 왜 LED 가 아니라 이것인가

지금 보드에 올라간 것은 레퍼런스 `led` 도메인이고, 그것으로 밟히는 것은 **선언 → 렌더 →
도구 호출 → 물리 동작**까지다. 증표도, 검증도, 권한 구간도 없다 — 평범한 원격 제어다.

특허가 「여기서 기술하는 것」이라고 못박은 것은 **선언 · 결속 · 동작** 셋인데, 그중 결속과
동작의 핵심(오프라인 검증·구간 평가)이 증거 0 으로 비어 있다. 그 자리를 실물로 세우는 것이
이 도메인의 목적이다. 무인보관함을 고른 이유는 청구항 2 의 수행 유형 중 **구간**이 가장
읽기 쉽고, 시계 없는 기기가 구간을 어떻게 판정하는지(청구항 4)가 같이 드러나기 때문이다.

**레퍼런스는 건드리지 않는다.** `domains/README.md` 의 규칙 그대로 `samples/` 아래에 두고
빌드에서 선택한다. 계약이 바뀌는 것이 아니라 능력을 시험하는 것이다.

## 1. 특허 구성요건 대비 — 세우는 것과 미루는 것

| 청구항 1 구성요건 | 이 설계 |
|---|---|
| 근거리 무선으로 **기기 신원 주장 + 제공 액션 명세**를 선언 | 세운다. 단 전송은 **USB CDC(유선)** — 근거리 무선은 BLE 보드의 몫 |
| 이동단말이 임의의 수단으로 **승인 획득** | 호스트가 이미 한다(`payment` 액션 → PayRunner). 데스크톱에서는 표면이 없어 설계대로 거절된다 |
| 결과를 **서비스 개인키로 서명된 증표**로 선언된 액션에 결속 | **세운다.** 증표 발급자는 테스트 하네스가 맡는다(원격 서비스 대역) |
| 증표를 이동단말 경유로 기기에 전달 | 세운다 — `voucher.present` 도구 |
| 기기가 **사전 프로비저닝된 공개키로 검증**, 선언한 액션과 대조, **통신망 없이** | **세운다.** Ed25519 검증, 링크는 있으나 검증에 쓰지 않는다 |
| **권한 구간**에 규율되어 기기가 국소적으로 판정 | **세운다.** 청구항 4 대로 근접 이벤트마다 받은 시각으로 추정치를 보정 |

**미루는 것 (이 컷 밖, 명시)**

- **보안요소(청구항 22)** — 이 보드에 없다. 키는 플래시에 둔다. *기기가 개인키를 보유한다*는
  구성요건은 성립하지만 *보안요소에 보유*는 성립하지 않는다. 이 차이를 문서와 화면 양쪽에 적는다.
- **기기 개인키 서명(§3.2 기기 주장)** — 이번 컷은 **검증 방향만** 세운다(서비스 → 기기).
  기기가 명세 해시에 서명해 서비스가 검증하는 반대 방향은 다음 컷.
- **근거리 무선** — BLE 보드로 옮길 때.
- **감사기록(청구항 19)** — 정족수 도메인의 몫.

## 2. 노드가 선언하는 것

`ui://app` + `ui://page/main` 은 레퍼런스와 같은 모양을 쓴다(애플리케이션 정의 + 페이지).
페이지가 선언하는 것은 셋이다.

1. **기기 신원** — 주입된 `id` / `name` / `version`, 그리고 `trust` 블록. 화면에 그대로 찍는다.
   키가 플래시에 있다는 사실도 찍는다. 서명된 것처럼 보이는 데모를 만들지 않는다.
2. **제공 액션과 조건** — 보관함 제안 둘.

   | itemId | 제안 | 수행 유형 | 조건 |
   |---|---|---|---|
   | `locker-4h` | 4시간 | 구간 | 승인 시각부터 4시간, 그 동안 몇 번이든 열림 |
   | `locker-24h` | 하루 | 구간 | 24시간 |

   `payment` 액션이 `seller` + `itemId` 를 싣는다. **금액은 싣지 않는다** — 셀러가 매긴다.
3. **현재 상태** — 잠김/열림, 남은 구간, 마지막 판정 사유.

**조건은 노드가 말한다.** 호스트는 이 기기에 대해 아무것도 모르는 채로 그리기만 한다.

## 3. 증표(voucher)

청구항 1 이 열거한 필드 그대로다. 임의로 늘리지 않는다.

```
{
  "deviceId":  "stm32.h723",          기기 신원
  "action":    "locker-4h",           선택된 액션 — 노드가 선언한 것 중 하나
  "notBefore": 1756500000,            권한 구간 시작 (unix seconds)
  "notAfter":  1756514400,            권한 구간 끝
  "target":    "B12",                 대상 참조 (이 보관함 칸)
  "session":   17,                    세션 값 — 단조 증가
  "sig":       "<base64url Ed25519>"  서비스 개인키 서명
}
```

**서명 대상은 정규화된 바이트열**이다. JSON 을 다시 직렬화해서 서명하면 공백 하나로 검증이
깨진다. 서명 입력은 필드를 고정 순서로 이어 붙인 문자열로 못박는다:

```
deviceId "\n" action "\n" notBefore "\n" notAfter "\n" target "\n" session
```

기기는 이 문자열을 **자기가 다시 만들어** 검증한다. 즉 기기가 읽은 값과 서명된 값이 같음이
보장된다 — 파서가 무시한 필드는 서명에도 들어가지 않는다.

## 4. 기기가 하는 검증 — 순서가 곧 규칙

전부 **fail-closed**. 하나라도 어긋나면 거절이고, 「일단 열고 나중에」는 없다.

1. **형식** — 필수 필드가 다 있는가. 없으면 거절.
2. **서명** — 사전 프로비저닝된 서비스 공개키로 Ed25519 검증. 실패면 거절.
   *여기까지 통신망을 쓰지 않는다.* 링크가 끊겨 있어도 같은 답이 나온다.
3. **기기 대조** — `deviceId` 가 이 기기인가. 남의 증표는 거절.
4. **액션 대조** — `action` 이 **이 노드가 선언한 액션 중 하나**인가. 선언에 없는 액션을
   담은 증표는 서명이 맞아도 거절한다(청구항 1 의 「대응함을 확인」).
5. **대상 대조** — `target` 이 이 칸인가.
6. **재생 거부** — `session` 이 지금까지 수용한 최대치보다 큰가. 아니면 거절.
7. **구간** — `notBefore ≤ 지금 ≤ notAfter` 인가. 아니면 거절.

통과하면 최대 세션 값을 갱신하고 구간을 보유한다. **이후 `locker.open` 은 통신 없이
구간만 보고 판정한다.**

### 4.1 재생 거부는 왜 단조 카운터인가

특허 §3.1 이 네 수단을 제시하고 「어느 것도 요건이 아니다」라고 한다. **단조 카운터**를 고른
이유: 발급자가 하나(테스트 하네스)라 기기별 순서를 보장할 수 있고, 저장이 **카운터 하나**로
일정하며 고갈되지 않는다. 발급자가 여럿이 되면 최근 증표 링 버퍼로 바꾼다 — 그때 N 은
「가장 긴 오프라인 구간 동안 예상되는 제시 횟수」로 정한다.

### 4.2 기기는 시계가 없다

STM32H723 에 배터리 백업 RTC 를 달지 않았다. 그래서 청구항 4 그대로 **근접 이벤트마다
제시되는 시각으로 추정치를 보정**한다.

- 호스트가 연결할 때 `time.sync` 도구로 현재 시각을 준다.
- 기기는 그 시각과 그 순간의 `uptime_ms` 를 함께 보관하고, 이후 시각을 `기준시각 +
  (현재 uptime − 기준 uptime)` 으로 추정한다.
- **보정을 무조건 받아들이지 않는다**(특허 §4.1 하위). 이미 보유한 추정치보다 **뒤로 가는**
  보정은 거절한다 — 시계를 되돌려 만료를 무르는 것이 가장 싼 공격이다.
- 시각을 한 번도 못 받았으면 구간 판정을 **할 수 없다** → 열지 않는다. 모르면 거절이다.

## 4.3 세션 — 기기가 1:1 이라서 생기는 것

**동시 접속은 도메인이 정하는 성질이지 기술 문제가 아니다.** 기준은 하나 — **그 동작이 기계를
점유하는가.**

| 기계 | 점유 | 동시 |
|---|---|---|
| **자판기** | 배출은 몇 초면 끝나고 기계는 곧 빈다 | **여럿** — 순서도 상관없다 |
| 무인빨래방 | 드럼이 42분간 잡힌다 | 하나 |
| 세차 | 베이가 잡힌다 | 하나 |
| **무인보관함** | 문이 4시간 잡힌다 | **하나** |

뒤 셋이 1:1 인 것은 선이 두 대화를 못 날라서가 아니라 **드럼이 하나, 베이가 하나, 문이
하나**여서다.

**수행 유형에서 읽어 낼 수 없다.** 세탁은 `once` 인데 점유하고, 배출도 `once` 인데 점유하지
않는다. 점유는 기계에 관한 별개의 사실이고 도메인만 안다.

그래서 이런 노드에는 **결제가 시간 제한을 가질 수밖에 없다.** 권한을 사 놓고 세션을 붙잡은 채
떠나면 기계가 멈춘다. 구간(4시간)과는 다른 층이다:

| | 무엇을 재나 | 무엇으로 재나 | 세션을 넘어 사나 |
|---|---|---|---|
| **권한 구간** | 대여가 얼마나 남았나 (시간·일) | 제시된 시각 + 단조 경과 | **산다** — 폰이 끊겨도 내 4시간이다 |
| **세션 창** | 승인하고 나서 **행동하기까지** (초·분) | 기기 자기 틱만 | **안 산다** |

세션 창은 **제시된 시각이 필요 없다.** 한 연결 안의 수십 초라 기기 틱으로 족하고, 바깥 누구도
그 값에 관여하지 않는다. 시각 보정을 둘러싼 §4.2 의 제약이 여기엔 아예 해당되지 않는다.

노드가 제안마다 값을 정한다 — 서 있는 사람이 쓰는 보관함은 30초, 거주자 패스는 2분.
`0` 이면 세션 창 없음이고 구간만 다스린다.

**세션이 끊기면 대기 중인 것은 함께 끊긴다.** 산 것은 안 끊긴다. 링크 상실에
`domain_session_reset()` 이 불려 세션 창과 열린 래치를 걷고, 권한 구간은 그대로 둔다.
끝난 세션은 완료된 세션이 아니다.

### 실측 — 배타성은 전송이 주지 않는다

| 전송 | 두 번째 피어 |
|---|---|
| TCP (노드 킷) | **거절** — 두 번째 연결을 즉시 끊는다 |
| BLE GATT | 링크가 하나 |
| **macOS USB CDC** | **열린다.** 같은 `/dev/cu.*` 를 두 번째로 여는 데 성공했다 — 바이트가 섞인다 |

이건 **고칠 결함이 아니라 어디서 지킬 수 있는가의 문제**다. 바이트 스트림에는 「누가
말하는가」가 없다 — 같은 포트를 두 호스트가 열면 그냥 섞이고, 도메인 코드로는 구분할 방법이
없다. **도메인이 지는 의무는 선언**이고, 피어 개념이 있는 전송(TCP·GATT)이 그것을 지킬 수 있는
자리다.

노드는 `bundle://manifest.json` 에 `"concurrency":"exclusive"` 로 선언하고 화면에도
「one person at a time」이라 적는다.

## 5. 수행

- `locker.open` — 보유한 구간이 살아 있으면 래치를 연다. 이 보드에는 래치가 없으므로
  **온보드 LED 가 래치를 대신한다**(열림=점등). 대체물이라는 사실을 화면과 문서에 적는다.
- 구간이 끝나면 **아무 통신 없이** 열리지 않게 된다. 만료를 알리는 메시지는 오지 않는다 —
  청구항 5 가 말하는 그대로다.

## 5.1 두 갈래 — 고정과 갱신

특허 §4.1.1 이 시각 추정치의 용도를 둘로 가르고, **자기 구성은 둘째**라고 못박는다. 둘은 한
가지의 변형이 아니라 요구가 다르다.

| | 고정 | **갱신** |
|---|---|---|
| 증표가 주는 것 | 확정된 구간 | **단위 요율로 상태 진입** |
| 기기가 정하는 것 | 만료 전인가 (참/거짓) | **얼마나 쓰였는가** |
| 끝나는 방식 | 스스로 만료 | **해제 이벤트** |
| 시각 추정치 | 역행만 막으면 족하다 | **양방향 구속** |
| 부재 중 계측 | 필요 없음 | **필수** — 제시 사이가 계측 대상 |
| 급전 | 간헐적이어도 됨 | **연속** |

**갱신형에서 기기가 지는 것 셋** (전부 플랫폼이 든다):

1. **같은 제스처가 두 전이를 모두 일으킨다**(§4.3.1). 비점유 기계에 검증된 제시 = 진입,
   점유 기계에 검증된 제시 = 해제. 따로 배울 인터페이스도 관리 인력도 없다.
2. **해제는 결코 누적액에 조건 지어지지 않는다**(§4.3.2). 편의가 아니라 **요건**이다. 정산까지
   해제를 유보하면 「물건 찾으러 온 사람에게 동전을 요구하는 코인 보관함」을 새 형태로
   재현한다. 기기에는 참조할 금액 개념 자체가 없다 — 다른 거절(서명·기기·액션·대상·재생)은
   그대로 적용된다. 해제도 **검증된** 제시다.
3. **누적은 통지로 한계 지어진다**(§4.3.3). 압류가 아니다. 통지는 서비스가 하고 **기기는 전
   구간 오프라인이며 알지 못한다** — 기기에 요구되는 것이 아무것도 없다.

`park-hourly` 는 30분을 단위로 갱신하고, 같은 차단기가 `park-flat-day` 라는 고정형도 판다.
**갈래는 제안마다이지 노드마다가 아니다.**

## 5.2 정전 — 무엇이 살아남는가

**대여가 전원 깜빡임에 사라지면 건물의 모든 문이 열린다.** 그래서 권한은 보드보다 오래 산다.

| | 살아남나 | 왜 |
|---|---|---|
| 권한(구간·갱신 진입) | **산다** | 산 것은 정전으로 무르지 않는다 |
| 재생 카운터(최대 세션 값) | **산다** | 잊는 기계는 이미 쓴 증표를 한 번 더 인정한다 |
| **시각 추정치** | **안 산다** | uptime 이 0 으로 돌아가고 제시된 시각은 남지 않는다 |
| 래치 | **안 산다** | 정전 뒤에 열려 있는 문은 아무도 열기로 하지 않은 문이다 |

그래서 되살아난 기계는 **대여를 들고 있으나 아직 판정할 수 없는 상태**로 깨어나고, 그렇게
말한다(`resumed after power loss - waiting for the time`). 다음 폰이 시각을 줄 때까지 안 연다.

**여기서 §4.1 의 「최근 증표 창 이전 금지」가 비로소 일한다.** 추정치가 없으니 역행 규칙은
비교할 대상이 없고, 첫 보정을 제시자가 원하는 아무 자리에나 둘 수 있다 — 그것을 막는 것이
이 하한 하나뿐이다. 온 부팅에서 발동하지 않는다고 지웠으면 정확히 여기서 없었다.

**저장은 타깃이 댄다** — 보드는 STM32 가 플래시 페이지에 흉내 내는 EEPROM, 가상 노드는 파일.
플랫폼은 *무엇을* 저장할지만 알고 *어디에* 는 모른다.

## 7. 암호

**Ed25519 검증만** 기기에 넣는다. 서명은 발급자(테스트 하네스)가 한다.

- 대칭 MAC(HMAC)로 하면 구현은 훨씬 싸지만, **기기가 증표를 위조할 수 있게 된다** — 특허가
  서비스 개인키로 서명하고 기기는 공개키로 검증한다고 못박은 이유가 그것이다. 이 차이는
  「구현 편의」가 아니라 청구항의 성질이라 바꾸지 않는다.
- 공개키는 **플래시 상수**로 심는다. 보안요소가 아니다 — §1 의 미루는 것에 적어 둔 그대로다.
- 검증 실패는 **거절**이다. 로그만 남기고 여는 경로를 두지 않는다.

보드가 없으면 사유를 말하고 skip 한다.

|---|---|---|
| 1 | 보드가 선언하고 이 티어가 렌더한다 | 제안 둘과 조건이 화면에 뜬다. 신원 줄에 「키는 플래시」가 찍힌다 |
| 2 | 시각 없이 여는 것은 거절된다 | `locker.open` → 거절, 사유 = 시각 미동기 |
| 3 | 유효한 증표는 수용된다 | `voucher.present` → 수용, `locker.status` 가 남은 초를 보고 |
| 4 | **연다** | `locker.open` → 열림. LED 로 물리 확인(보드에 되물어) |
| 5 | **서명이 틀리면 거절** | 한 바이트 바꾼 증표 → 거절. 이것이 검증이 도는지 보는 유일한 방법 |
| 6 | **남의 기기 증표는 거절** | `deviceId` 만 바꾼 유효 서명 → 거절 |
| 7 | **선언 안 한 액션은 거절** | 서명은 맞고 `action` 이 목록 밖 → 거절 |
| 8 | **재생은 거절** | 같은 `session` 재제시 → 거절 |
| 9 | **만료는 통신 없이 닫힌다** | 짧은 구간(수 초) 증표 → 구간 뒤 `locker.open` 거절. **그 사이 아무것도 안 보낸다** |
| 10 | **시계 되돌리기는 거절** | 뒤로 가는 `time.sync` → 거절, 구간 판정 불변 |
| 11 | **세션 창이 닫히면 거절하되 대여는 살아 있다** | 창 경과 후 `locker.open` 거절 · `remaining` 은 그대로 |
| 12 | **전진 점프는 거절되고 서 있던 권한은 산다** | `+1년` `time.sync` 거절 · 대여 불변 |
| 13 | **갱신형은 부재 중에도 누적한다** | 아무것도 안 보낸 채 경과 → `units` 증가 |
| 14 | **갱신형은 만료되지 않는다** | 시간이 지나도 `expired` 아님 |
| 15 | **같은 제스처가 해제하고 총액을 확정한다** | 두 번째 제시 → `released units=N` |
| 16 | **대여가 정전을 넘는다** | 재부팅 후 `remaining` 살아 있고 `resumed after power loss` |
| 17 | **시계는 안 넘는다** | 재부팅 직후 `time=unknown` · 열지 않음 · 래치 안 올라옴 |
| 18 | **재부팅 후 첫 보정의 하한** | 대여 시작보다 앞선 `time.sync` 거절 |

5~10 이 이 설계의 본체다. 1~4 만 통과하는 구현은 **검증하는 척하는 노드**다.

## 9. 착수 전 결정 필요

1. **이 설계로 진행할지** — 특히 §7(Ed25519 고정) 과 §1 의 「미루는 것 넷」.
2. **증표 발급자를 어디에 둘지** — 이번 컷은 테스트 하네스. 실제 서비스(사스)로 옮기는 것은
   별도 축이고, 옮길 때 서명 입력 정규화(§3)가 계약이 된다.
3. **레퍼런스 승격 여부** — `samples/` 에서 증명된 뒤 계약을 스펙(`specs/embedded/`)과
   레퍼런스로 올릴지. 올린다면 사용자 승인이 필요한 정전 변경이다.
